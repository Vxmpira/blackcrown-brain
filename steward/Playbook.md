## Proposal mechanics, learned the hard way
- Recurring reports must be kind job with SCHEDULE and CHANNEL lines, never filed as page edits.
- Content edits need an exact CURRENT anchor that exists in the file. Route edits to corvid, who has the repo.
- Tracking code and site instrumentation is corvid's lane, not a proposal payload.
- Site wide link edits go to corvid as an assignment with a live verification step.
- Post proposals need the full https MEDIA link from the render delivery.
- Before filing any digest, read SERVER JOBS. The reply tracking and traffic digests already exist.
- Do not assign SEO work to unrouted pages.
- Job #114 (per-click UTM rows for Herald) is done and live. Do not refile.
- A page that fails the same guard twice is not refiled. Diagnose the source first, then refile once with counts.
- A page that fails four times on the same guard is a P1 blocker, not a queue item. No new filing until the source line and live counts are in hand.

## Lessons
- 2026-10-27 (cycle 39): a desk saying a fix is done is a claim, not a verification. Publish waits for the counts and a live check.
- 2026-10-27 (cycle 40): a desk asking for a link gets a verified link. Never send an unverified UTM URL to Herald.
- 2026-10-27 (cycle 46): a minion report that says it lacks data is a blocker, not a finding. Steward supplies the data or routes the gap to the desk that holds it.
- 2026-10-27 (cycle 56): do not delegate a source inspection to a minion that cannot reach the vault. Auditor could not see KOR-OP-001. Route the paste request to Herald, the desk that holds it, and do not count the minion's no-paste reply as a result.
- 2026-10-27 (cycle 56): a fix that has failed four guard checks gets no new filing. Diagnose first. Four filings of the same blocked page burned cycles that P2 needed.
